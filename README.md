# 알람 원인 추적 대시보드 (시제품)

> 팀 익스플래닛 · GEW KOREA 2026 기업가정신 챌린지 최종 결과물
> 모든 설비·래더·조치이력은 **시연용 가상 데이터**입니다.

배터리 전극·조립 라인 31대의 실시간 상태를 FMCS처럼 보여주고, 알람이 나면 **PLC 래더를 코드로 거슬러 올라가 알람을 성립시킨 조건과 그 원천(현장 입력·외부 신호·래더 로직)** 을 찾습니다. 조치는 DB에 쌓이고, 쌓인 이력을 분석해 **"리셋만으로 풀리던 알람은 래더를 고치자"** 처럼 다시 안 나게 하는 개선안을 역으로 제안합니다.

## 범용 AI 채팅에 로그를 붙여넣는 방식과의 차이

AI가 더 똑똑해서가 아니라, **우리 설비의 PLC 래더·디바이스 코멘트·조치이력에 연결돼 있어서** 다릅니다. 아래는 '알람 로그만 붙여넣고 질문하는 경우'와 비교한 것이며, 래더·이력까지 함께 제공하면 범용 AI도 일부는 할 수 있습니다.

| | 알람 로그만 붙여넣고 질문할 때 | 이 도구 |
|---|---|---|
| 근거 | 일반적인 설비 지식. 질문 방식에 따라 답이 달라질 수 있음 | 설비에 연결된 PLC 래더·코멘트·조치이력. 같은 입력이면 같은 결과(코드 계산) |
| 알람 원인 | 래더가 없으면 원인 후보를 일반론으로 제시 | 알람 코일 → 실제로 성립한 분기 → 원천까지 추적, 스텝 번호와 발생 순간 값 표시 |
| 알람 없이 멈춘 설비 | 자동운전 조건 회로를 모르면 판단 근거가 부족 | 자동운전 조건 회로에서 막힌 접점을 표시 |
| 재발 방지 | 과거 조치 기록이 없으면 일반 권고 | 조치이력의 측정값·해결률로 래더 검토안·예방정비 주기·매뉴얼 보강을 근거 수치와 함께 제안(추정치) |
| 보안 | 로그·프로그램을 외부 서비스로 보내야 함 | 추적·분석은 코드가 처리. AI는 선택이며 결과 몇 줄만 LOT·사번·IP를 가린 뒤 전송 |
| 기록 | 대화가 끝나면 현장 기록으로 남지 않음 | 조치 기록이 다음 진단·제안·인수인계에 반영되고, 수정·삭제 이력이 보존됨 |

## 개선 제안 규칙 (모두 코드 계산 · rules-1.3)

1. **지속 판정 추가(래더 수정)** — 경알람이 리셋만으로 60% 이상 풀리고 신호가 짧으면, 리셋 해결 건의 80%를 거르는 가장 짧은 시간(1초 이하)으로 지속 판정 타이머를 끼운 래더안. 품질 알람은 지연 동안 통과하는 전극 길이를 함께 표시
2. **원인 점검 권고** — 리셋으로 풀려도 신호가 길거나, 중알람·안전·설비 보호 알람이면 래더로 거르지 않음
3. **타이머 설정값 검토(경알람만)** — 응답이 현재 기준보다 길고 1.5배 이내에서 리셋·재시작으로 풀린 건이 몰리면 90% 값 + 여유를 검토 출발값으로 제시(기준을 줄이는 제안은 만들지 않음, 안전 근거 아님 → 확인 항목 필수). 중알람·안전·설비 보호 알람은 기준을 늘리지 않고 응답 지연 원인 개선을 권고
4. **예방정비 주기** — 알람 뒤 같은 교체·청소·보충 간격이 일정(변동 35% 이하)하면 평균의 85% 주기와 설비별 다음 권장일
5. **매뉴얼 보강** — 매뉴얼에 없는 조치로 3번 이상 해결되면 초안 제시(7일 안 재발률로 임시 조치 여부 확인)
6. **설비 편중 조사** — 같은 프로그램 설비군 중 한 대에 몰리면 그 설비의 조건 차이부터 조사
7. **송수신 경계 공동 점검** — 외부 신호가 원천이고 대기가 길면 협의 자료(동시 다발 횟수 포함)
8. **판단 보류** — 리셋 위주인데 측정값이 부족하면 제안하지 않고 필요한 자료만 표시

**독립 기간 검증(rules-1.3)** — 기준은 앞 60일에서만 고르고 최근 30일에 적용하되, 결과를 조치 유형·결과별로 나눠 봅니다(리셋 해결 / 리셋 외 조치 / 리셋 미해결). 리셋 외 조치가 억제되면 '미달', 리셋 미해결이 억제되면 '확인 필요'이며 확인 전에는 1대 시범으로 가지 않습니다. E-1105는 리셋 해결 36/36 억제 · 리셋 외 조치 0/6 · 리셋 미해결 1/1 억제 → **확인 필요**입니다.

효과 수치는 조치이력의 측정값으로 다시 계산한 **추정치(가정 조건에서 억제됐을 것으로 추정되는 기록 수 — '불필요한 알람 제거' 실적이 아님)** 이며, 실증은 "섀도 모드(래더는 그대로, 도구만 병행 계산) → 1대 시범 → 확대" 순서로 합니다. **이 도구는 PLC에 쓰지 않습니다.**

## DB와 AI는 어떻게 연결되나

**판단은 코드가 하고, AI는 데이터를 다듬는 보조 역할만 합니다.** 개선 판단의 근거는 DB에 쌓인 관측 데이터와 규칙 코드이며, AI 연결 자체는 판단의 근거가 아닙니다.

1. **쌓기** — 조치이력은 `action_logs`, 대응 처리 상태는 `alarm_work`에 저장됩니다. 실제 도입에서는 PLC 게이트웨이(읽기 전용)가 원천 신호의 켜짐·꺼짐 시각과 요청·응답 신호 쌍을 자동으로 기록합니다. 알람이 켜져 있던 시간과 원천 신호 지속 시간은 따로 잽니다.
2. **정리** — 작업자가 말하듯 적은 메모를 [정리] 버튼이 표준 칸으로 옮깁니다(키워드 규칙). 원문을 보존하고 근거 문구를 보여 주며, 원인은 후보로만 제시합니다. 문장에서 뽑은 측정값은 '작업자 기재값'으로 표시합니다. AI 분류는 `AI_NORMALIZE=true`일 때만 켜지는 실험 기능입니다.
3. **판단** — 규칙 엔진이 제안을 만듭니다. 기준은 앞 60일에서만 고르고 마지막 30일에 적용해 독립 기간 검증을 하며, 근거가 부족하면 '판단 보류'로 둡니다. 제안마다 입력 기간·규칙 버전·계산 시각이 남습니다.
4. **실증** — 섀도 모드(래더 그대로, 도구만 병행 계산) → PLC 담당 승인 → 1대 시범 → 확대. 검토 상태, 섀도 결과, 시범 결과는 서로 다른 것으로 저장합니다(승인은 효과의 증거가 아님).
5. **AI 패턴 탐색**은 이번 범위에서 제외합니다. 하더라도 담당자가 가설을 규칙으로 정의하고, 탐색에 쓰지 않은 기간에서 검증한 뒤에만 등록합니다.

**30초 설명** — 지금은 조치이력을 DB에 저장하고, 규칙 코드가 개선 후보를 계산합니다. 실제 도입에서는 PLC의 신호 변화와 응답 시간을 읽기 전용으로 수집해, 작업자가 확인한 조치 기록과 연결할 계획입니다. 후보는 별도 기간 데이터와 섀도 모드로 검증하고, 승인 뒤 한 대에서 시범 적용합니다. AI는 마스킹된 결과를 쉽게 설명하며, 도구는 PLC를 직접 변경하지 않습니다.

## 알려진 한계

- `ALLOW_DEMO_RESET`은 관리자 인증이 아니라 켜고 끄는 스위치입니다. 실제 운영에는 로그인·권한이 필요합니다(로드맵).
- AI 호출 한도는 서버 인스턴스마다 따로 셉니다. 실제 운영에서는 공용 카운터(DB 등)로 합산해야 합니다.
- 조치 기록 1건 = 알람 1건으로 셉니다. 반복 의심 배지·MTBF/MTTR 근사가 기록을 많이 남긴 설비에 불리할 수 있어, 실제 도입에서는 알람 사건 ID로 여러 조치를 묶고 PLC 운전 시간·정지 이벤트로 계산합니다.
- 발생 전후 신호 파형은 수집하지 않아 보여 주지 않습니다(PLC 게이트웨이 필요). 가상 데이터라도 미수집 값은 만들지 않습니다.
- 대응 상태·담당은 로그인 없이 입력합니다. 실제 운영에는 사용자 인증·권한이 필요합니다.


| 변수 | 효과 |
|---|---|
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | 조치이력·검토·변경 기록을 Supabase에 저장 (`supabase/schema.sql` 실행 후, 화면의 '시연 데이터 초기화'로 시드 입력). 키는 서버에서만 사용 |
| `ANTHROPIC_API_KEY` (`ANTHROPIC_MODEL`, `AI_DAILY_LIMIT`) | 알람 상세의 쉬운 설명을 AI 문장으로(접속지당 분당 6회·하루 기본 300회 제한). 없으면 규칙 기반 문장 |
| `ALLOW_DEMO_RESET=true` | Supabase 모드에서 '시연 데이터 초기화' API 허용 (기본은 막힘) |
| `AI_NORMALIZE=true` | 현장 메모 정리에 AI 분류를 함께 사용(실험 기능, 정해진 선택지 안에서만) |
